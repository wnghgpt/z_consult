# 고객 상담 데이터 정리 및 분석 프로젝트

## 최신 구현 상태: Supabase 연결

상담 앱 전용 `.env.local`에 URL과 공개키를 설정했다. 로그인·권한 확인·검토용 임시 저장 UI를 구현했다. 파일 선택만으로는 전송하지 않으며, 로그인 후 저장 버튼을 누르면 복원 자료와 원본 셀 내용이 Supabase로 전송된다. 고객·상담 본 테이블 반영은 아직 구현 전이다.

인증 설정 엔드포인트의 HTTP 200 응답을 확인했다. 실제 사용자 로그인·DB 저장은 스키마 적용 및 계정 권한 설정 이후 검증해야 한다. 로그인 세션은 `z-consult-auth-v1` sessionStorage 키로 분리하고 계정 변경 시 미리보기를 비운다. 관리자 키는 사용하지 않는다.

관리자는 SQL 마이그레이션 적용, `consult` 스키마 API 노출, 상담 계정의 `app_metadata.z_consult=true` 설정을 해야 한다. 공개키만으로는 이 작업을 수행할 수 없다. 기존 API 노출 스키마는 유지한다. 이후 앱에서 이메일·비밀번호로 로그인한다.

상담 고객 데이터를 주기적으로 엑셀로 가져와 정리하고, DB에 누적하여 React 화면에서 통계·시각화·전략 분석에 활용한다. 원본 시스템은 API로 데이터를 제공하지 않으므로 **수동 엑셀 수집 → 자동 복원·검증 → DB 반영**을 기본 흐름으로 한다.

이 문서는 구현 전 요구사항과 설계 방향을 정리한 것이다. 아래 기능이 구현되었다는 의미는 아니다.

## 현재 구현 및 실행

첫 단계인 독립 React 앱과 XLSX 복원 미리보기를 구현했다. DB 저장, 중복 병합, 수동 상담 입력, 사진 업로드와 분석 화면은 아직 구현하지 않았다.

```bash
cd z_consult
npm install
npm run dev
npm test
npm run build
```

브라우저에서 파일을 선택하거나 드래그하여 읽는다. 시트 선택, 검색, 검토 항목 필터, 고객별 원본 셀 대조를 제공한다. 데이터는 메모리에만 보관되며 새로고침하면 사라진다. 파일 선택 시에는 서버로 전송하지 않는다. 명시적으로 임시 저장 버튼을 누르면 현재 시트의 자료를 Supabase에 전송한다. 지원 형식은 XLSX, 파일 제한은 20MB이다.

파서는 샘플의 고객 시작·상담 날짜/상태 쌍·수술 후보 패턴을 사용한다. 원본 No.는 고정 고객번호로 확인되었다. 복수 날짜 칸은 여러 부위를 다룰 수 있으므로 칸 수를 방문 수로 해석하지 않는다. 부위별 연결이 불명확한 경우 복원 후보로 표시한다. 생년월일·연락처는 추정 복원하지 않는다. 규칙과 일치하지 않는 열은 원본과 함께 검토 대상으로 남긴다. 원본 파일은 저장소에 포함하지 않는다.

## 프로젝트와 DB 구성

- 기존 얼굴 분석 앱과 코드·API·환자·의존성을 공유하지 않는 독립 React 앱이다.
- 기존 Supabase 프로젝트의 DB와 Storage 인프라만 사용한다. 별도 FastAPI/Python 서버는 초기 범위에 없다.
- 상담 앱 전용 스키마·비공개 사진 버킷과 접근 정책으로 분리할 계획이다. 실제 DB 연결이나 변경은 아직 하지 않았다.
- 기본 테이블은 patients, consultations, procedures, photos, imports의 5개로 시작한다.
- 엑셀 복원은 브라우저, 검증·중복 처리·일괄 저장과 통계 집계는 DB 함수에서 담당할 계획이다.
- 원본 메모와 직접 입력 메모를 별도 컬럼으로 보존한다. imports에 처리 결과와 검토·변경 내역을 기록한다.
- 기존 앱과 사용량을 공유하므로 무료 한도와 사진 용량은 연결 시 확인한다.
- LLM은 필수가 아니다. 이후 메모 분류·요약만 선택적으로 도입한다.

```text
z_consult React → Supabase 상담 전용 DB 영역
              → 비공개 Storage (사진)
```

## 화면 및 후속 구현

홈은 ② 대시보드 중심형으로 구성하고 전체 자료 테이블과 분리한다. 차트를 클릭하면 해당 조건의 자료 목록으로 이동한다. 개발 순서는 복원 미리보기 → DB 적재·접근 제어 → 전체 자료·고객 상세 → 사진 → 홈·상세 분석이다.

고객 상세에서 공통 특이사항과 상담별 미예약 사유·후속 연락 기록을 입력한다. 사진은 실제 파일을 비공개 Storage에 보관하고, DB에 고객·수술 연결, 버킷·경로, 촬영일, 전후·경과 구분, 각도를 기록한다. 만료되는 URL은 영구 저장하지 않는다.

구현 파일:
- `src/lib/parser.js`: UI와 분리된 복원 규칙
- `src/lib/workbook.js`: XLSX 읽기 및 시트별 복원
- `src/main.jsx`, `src/style.css`: 업로드·미리보기·원본 대조
- `tests/parser.test.js`: 합성 데이터 기반 경계·복원 검증

## 입력 파일과 확인된 문제

검토한 파일:

- `고객목록_정리_Book.xlsx`: 정리본 시트, 데이터 594행·41개 항목. 행 수가 고유 고객 수를 의미하지는 않는다.
- `제목 없는 스프레드시트.xlsx`: 깨진 원본 예시. 고객 시작 행 4개를 확인했다.

원본에는 고객 기본정보, 소개 정보, 상담일·상태·항목·내용, 담당자, 수술·시술일과 상태 등이 포함된다. 실제 개인정보와 상담 내용은 이 문서나 소스 저장소에 복사하지 않는다.

확인된 구조 문제:

- 한 고객의 여러 줄 메모가 여러 행으로 분리된다.
- 메모 뒤의 상담·수술 정보가 왼쪽 열로 이동한다.
- 수술 정보가 상담 내용의 마지막 행에 붙기도 한다.
- 날짜가 엑셀 일련번호로 저장되기도 한다.
- 생년월일과 전화번호가 숫자로 저장되어 앞자리 0이 손실되었을 가능성이 있다.
- 같은 이름이 여러 행에 존재한다. 이름만으로 고객을 합칠 수 없다.

고객별 행 수가 다르므로 일정한 행 수로 묶거나 빈 행을 지우는 방식으로 처리하지 않는다. 샘플에서 확인한 패턴이 모든 파일에 적용된다고 가정하지 않는다.

## 기본 처리 흐름

```text
원본 엑셀 업로드 및 추출 범위 기록
    ↓
원본 보관 및 파일 구조 확인
    ↓
고객 단위로 행 묶기
    ↓
기본정보 / 메모 / 상담 / 수술·시술 구간 복원
    ↓
날짜·항목·상태 표준화
    ↓
고객 식별 및 방문 중복·변경·재방문 판별
    ↓
검증 및 충돌 분류
    ↓
정상 데이터 DB 반영 / 불확실한 데이터 검토 보류
    ↓
반영 결과 및 변경 이력 기록
```

초기에는 미리보기로 복원 정확도를 확인하고, 검증된 규칙에 해당하는 데이터는 자동 반영하도록 한다. 자동화가 불확실한 정보를 추측해서 저장하는 방식이 되어서는 안 된다.

## 엑셀 복원과 표준화

- 고객번호와 기본정보 배치 등을 조합해 고객 시작을 찾는다.
- 다음 고객 시작까지의 행을 분석해 메모와 상담·수술 구간을 분리한다.
- 날짜·상태·항목의 조합과 구간 순서로 밀린 열을 복원한다.
- 여러 줄 메모는 원래 순서와 줄바꿈을 보존한다.
- 원문과 표준화된 값을 함께 보관한다. 같은 의미의 상담항목이나 상태는 명시적인 매핑으로 집계한다.
- 날짜는 파일의 날짜 체계와 필드 의미를 확인해 변환한다. 생년월일 같은 숫자 문자열을 무조건 엑셀 날짜로 해석하지 않는다.
- 전화번호·생년월일의 손실된 자릿수는 근거 없이 복원하지 않는다. 검증할 수 없으면 보류하거나 불확실성을 기록한다.
- 인식하지 못한 구조, 필수값 누락, 불가능한 날짜 등은 원본 위치와 함께 검토 대상으로 남긴다.

## 고객 식별과 중복·재방문 처리

**고객 중복과 방문 중복을 별도로 판단한다.** 같은 고객이라는 이유로 방문 기록을 삭제하지 않는다.

| 입력 상황 | 처리 |
| --- | --- |
| 같은 고객 + 같은 방문 + 같은 내용 | 중복으로 건너뜀 |
| 같은 고객 + 같은 방문 + 상태·내용 변경 | 기존 방문 업데이트, 변경 전후 이력 보관 |
| 같은 고객 + 새로운 방문 | 해당 고객에 방문 이력 추가 |
| 처음 보는 고객 | 고객과 방문 이력 생성 |
| 고객 또는 방문 식별이 불확실 | 검토 대상으로 보류 |

식별 기준:

- 고객은 원본 시스템의 고정 고객번호를 우선 사용한다.
- 방문은 원본 방문·예약번호가 제공된다면 이를 우선 사용한다.
- 방문번호가 없다면 고객번호, 날짜, 항목, 담당자 등을 조합하되, 이를 항상 고유한 식별자로 보지는 않는다.
- 예약일 변경과 같은 날 여러 상담을 구분해야 한다. 날짜 변경만으로 재방문을 만들거나 같은 날짜라는 이유로 병합하지 않는다.
- 파일 전체 중복 확인과 방문 단위 중복 확인을 모두 수행한다. 파일 내용이 달라도 추출 기간이 겹칠 수 있다.
- 같은 파일 재업로드나 처리 재시도로 고객·방문이 중복 생성되지 않아야 한다.
- 중복은 원본 삭제가 아니라 DB에 추가 저장하지 않는 방식으로 처리한다.

## 기간 중첩과 변경 충돌 처리

### 추출 범위

업로드마다 추출 기간, 조회 조건, 추출 시각을 가능한 범위에서 기록한다. 알 수 없는 값은 미확인으로 남긴다. 업로드 시각과 원본 추출 시각을 구분한다.

이번 파일에 고객이나 방문이 없다는 사실만으로 기존 데이터를 삭제하거나 취소 처리하지 않는다. 기간이나 필터가 다른 부분 목록일 수 있다.

### 과거 파일과 최신 상태

오래된 파일을 나중에 올렸다고 최신 상태를 덮어쓰지 않는다. 원본 수정 시점 등 신뢰할 수 있는 근거를 사용하고, 우선순위를 판정할 수 없는 변경은 충돌로 표시한다. 업로드가 늦었다는 이유만으로 최신 데이터라고 판단하지 않는다.

### 빈칸과 삭제

빈칸은 기본적으로 기존 정보를 지우지 않는다. 정보 없음, 추출 누락, 명시적인 삭제를 구분하는 규칙이 필요하다. 취소·삭제는 명확한 원본 상태나 검토 결과가 있을 때 반영한다.

## 데이터 모델 방향

| 구분 | 역할 |
| --- | --- |
| 고객 | 원본 고객 식별번호와 기본정보 |
| 상담·방문 | 고객별 상담일, 상태, 항목, 담당자, 내용 |
| 수술·시술 | 일정, 실제 진행 여부, 상태, 항목 |
| 상담과 수술·시술 연결 | 전환 분석에 필요한 관계와 연결 근거 |
| 업로드 이력 | 원본 파일, 추출 범위, 처리 상태, 처리 규칙 버전, 결과 집계 |
| 원본·복원 데이터 | 시트·행·셀 위치, 원문, 정규화 결과, 검증 결과 |
| 변경 이력·검토 항목 | 변경 전후 값, 변경 근거, 충돌과 수동 처리 결과 |

한 고객의 여러 상담 중 어떤 상담이 수술로 이어졌는지 근거를 남긴다. 관계가 불분명하면 미확정으로 두고 임의로 연결하지 않는다. 구체적인 테이블과 관계는 원본 필드 의미 확인 후 확정한다.

## 검증, 추적, 되돌리기

- 복원된 각 기록에서 원본 파일과 시트·행·셀을 찾을 수 있어야 한다.
- 업로드 결과는 `신규 고객 / 신규 방문 / 기존 방문 수정 / 중복 건너뜀 / 확인 필요 / 오류`로 구분해 보여준다. 고객과 방문 집계는 단위가 다르므로 단순 합계하지 않는다.
- 검토 화면에서 원본과 복원값을 비교하고 수정·확정 후 다시 반영할 수 있어야 한다.
- 처리 도중 실패해도 일부 관계만 저장되거나 재시도 시 중복이 생기지 않게 반영 단위를 관리한다.
- 잘못된 업로드의 영향을 되돌릴 수 있도록 생성·수정 내역을 기록한다. 이후 다른 업로드가 수정한 데이터는 무조건 과거 값으로 되돌리지 않고 충돌을 확인한다.
- 원본과 DB의 접근 권한을 제한하고, 분석 화면은 목적에 맞게 개인정보를 마스킹한다. 로그에 원문 개인정보가 불필요하게 남지 않도록 한다.
- 원본 보관·백업·삭제 정책을 정한다. 실제 고객 파일은 코드 저장소에 포함하지 않는다.

## 구현 전에 확인할 사항

- 원본 `No.`는 추출 시점이 달라도 유지되는 고정 고객번호로 사용자 확인을 받았다.
- 정리본의 `번호`와 원본 `No.`의 관계를 확인한다. 동일하다고 가정하지 않는다.
- `상담일1/2`, `수술일1/2`, `시술일1/2`와 각 상태가 무엇을 뜻하는지 확인한다. 예약일·실제 진행일·별도 방문인지 확정해야 한다.
- 방문·예약번호, 원본 수정 시각을 추가로 가져올 수 있는지 확인한다.
- 추출 기간과 검색 조건의 기준이 상담일인지 수술일인지 등 목록의 의미를 확인한다.
- 파일 구조가 다른 사례와 예약 변경, 취소, 같은 날 복수 상담 사례를 확보한다.

## 단계별 개발 범위

1. **복원 파서와 확인 화면**: 깨진 엑셀을 고객 단위로 복원하고 원본과 대조한다.
2. **식별·중복·변경 판별**: 고객과 방문을 구분하고 재방문, 예약 변경, 기간 중첩을 처리한다.
3. **DB 반영과 운영 기능**: 자동 반영, 검토 보류함, 업로드 이력, 재시도, 되돌리기를 구현한다.
4. **통계와 시각화**: 검증된 데이터와 명시적인 지표 정의로 대시보드를 만든다.
5. **전략 분석**: 후속 상담 대상, 재연락 시점, 항목·소개 경로별 개선 지점을 분석한다. AI 메모 분석은 이후 범위로 둔다.

1차 데이터 정리 완료 기준은 반복 업로드로 중복이 생기지 않고, 재방문이 보존되며, 불확실한 데이터가 분리되고, 반영된 값을 원본까지 추적할 수 있는 상태다.

대표 검증 사례는 동일 파일 재업로드, 기간이 겹치는 파일, 실제 재방문, 예약일 변경, 같은 날 복수 상담, 과거 파일의 뒤늦은 업로드, 빈칸 업데이트, 복원 불가 행, 실패 후 재시도를 포함한다. 테스트에는 비식별화 또는 합성 데이터를 사용한다.

## 통계·전략 활용 시 별도로 정할 기준

| 분석 | 목적 |
| --- | --- |
| 월별 상담 고객 수·상담 건수 | 고객 수와 방문 수를 구분해 유입 추세 확인 |
| 상담항목별 수술 전환율 | 후속 상담 개선 대상 파악 |
| 상담 후 수술까지의 기간 | 재연락 시점 검토 |
| 소개 경로별 유입·전환 | 소개 고객 관리 방향 설정 |
| 상담 후 미진행 고객 | 후속 상담 대상 정리 |

전환율에는 완료 상태, 분모가 되는 상담·고객의 기준, 상담 후 관찰 기간, 여러 상담의 기여를 계산하는 기준이 필요하다. 최근 상담 고객을 바로 미전환으로 확정하지 않는다. 미확정·보류 데이터의 집계 포함 여부와 데이터 추출 범위도 표시한다.

정리본에는 별도 결제금액·광고비 항목이 없다. 원본 메모에는 결제 관련 문구가 일부 있지만, 실제 매출로 사용할 수 있는 값인지는 검증되지 않았다. 매출·광고 수익성 분석에는 별도의 신뢰할 수 있는 결제·비용 데이터가 필요하다.

## DB 준비 및 비교 계획 구현

5개 테이블과 RLS, 임시 적재 RPC를 로컬 SQL로 작성했다. 원격 Supabase에는 적용하지 않았다. 이전 엑셀을 추가로 선택해 적재 전 비교 근거를 볼 수 있다. 실제 DB 대조·본 테이블 반영·자동 되돌리기는 아직 구현 전이다. [DB 설계 및 적용 순서](docs/database-plan.md)를 참고한다.
